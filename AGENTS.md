### Critical: Build Cache Rules
- **NEVER use `NOCACHE=1`** unless intentionally rebuilding the entire tree — it passes `--no-cache` to every `docker build`, destroying all Docker BuildKit cache across all packages.
- **NEVER delete `out/*/` directories** unless you accept a full rebuild — the Makefile depends on OCI layouts at `out/{stage}-{name}/index.json` as build targets. Deleting them breaks dependency resolution.
- **To force a single target rebuild:** only remove that target's output dir, e.g. `rm -rf out/distro-busybox-dev && make distro-busybox-dev`. Leave dependency dirs (`out/core-busybox`, `out/user-linux-server`, etc.) intact.
- **Docker BuildKit is content-addressed:** if source files change, only affected stages rebuild automatically (no NOCACHE needed).

### Distro package layout (Aug 18-19 refactor, lance/distros)
- Distro subpackages split three ways per variant: **default** = live layout (rootfs contents + `/boot` with the three boot objects [vmlinuz, initramfs, cmdline] — no UKI in the live layout); `docker run` gives a shell on the booted filesystem. **`-img`** = scratch + `/disk.img` (box-disk takes the full live layout and does all the packing). **`-vm`** = service-qemu + `/disk.img`.
- `box-uki` (packages/box/uki) is a **pure function**: (vmlinuz, initramfs, cmdline [, os-release]) → the final EFI layout containing ONLY the UKI at `EFI/BOOT/BOOTX64.EFI` (ukify + systemd-stub; deterministic, same inputs → same bytes). If os-release is omitted, ukify 260.2 auto-falls back to the build image's `/etc/os-release` — box-disk always passes the distro's own file explicitly.
- `box-disk` (packages/box/disk) is the single disk assembler, orchestrating the inner boxes: box-uki on `/boot/*` → ESP tree → FAT boot.img sized exactly to the UKI (busybox mcopy: `mcopy -sm $ESP/EFI ::/` puts the tree at the FAT root — copying `$ESP` itself nests it under `::/esp`), box-erofs → system.img (live layout minus `/boot`), box-gpt → GPT `disk.img`.
- **ESP/disk sizing (Aug 20):** the ESP is sized to the UKI, not a fixed 512 MiB. **Always FAT32 with 4 KiB clusters** (padded to FAT32's 65525-cluster minimum, ~256 MiB). UKI volume serial pinned (`-i 0x53544147`). `box-gpt` derives the ESP partition size from the boot.img file; ESP-only (unikernel) disk = ESP + 2 MiB tail for the alternate GPT header. **Why not FAT16:** an earlier revision used FAT16 with 16 KiB clusters for UKIs under 1 GiB, and it booted in QEMU (edk2 202508) but **never booted on AWS Nitro UEFI** (instance sat `running`, no serial output, no status checks, port 22 closed) — the old Nitro firmware does not boot that ESP. The pre-UKI AWS-working image used FAT32, and FAT32/4KiB ESPs boot on AWS (verified Aug 20: port 22 open ~45 s after launch). Enclave disk.img: 528 → **259 MiB** (257 MiB ESP).
- The booted system **never mounts the ESP** (no `/boot`, no vfat mount in the guest): rcS/initramfs write progress markers by raw `dd` seeks to the ESP tail. So the final ESP legitimately contains only the UKI (kernel/initrd/cmdline live inside it, verified byte-identical in [2]).
- `box-grub` with `TREE_ONLY=1` leaves the ESP tree at /boot + /efi instead of packing a FAT image (embed distro still uses the default packing path; embed is a separate GRUB/limine flow).
- Consumers of disk.img use the `-img` subpackage: `make distro-enclave-dev-img`, `out/rootfs/distro-enclave-dev-img/linux_amd64/disk.img`; aws-ami extracts via plain `cp` from the local export (the -img image has no command, so `docker create` on it fails).
- erofs images are NOT bit-deterministic across builds (internal NIDs/layout differ), so any measurement pin over the erofs bytes changes per build; the binding stays valid because local artifacts and the live system come from the same build. The UKI itself IS bit-deterministic for fixed inputs (same kernel/initrd/cmdline/osrel/stub → same bytes, e.g. `c913d89c…` across rebuilds in disk mode). Note: in unikernel mode the initrd embeds the erofs, so the UKI changes per build too.
- **Re-verified after restructure:** disk with UKI-only ESP boots QEMU and `verify-binding --uki` → **VERDICT: BOUND** (PCR4/5/9/11 pins unchanged from the pre-restructure BOUND run).

### Unikernel enclaves (Aug 19, lance/distros)
- Enclaves run fully from RAM: `box-disk` with `UNIKERNEL=1` packs the OS as erofs, wraps it as `/system` inside a tiny cpio (5 static klibc utils + `init-loop` as `/init`), and uses that cpio as the UKI's `.initrd`. The kernel unpacks it to RAM; `/init` does `losetup /dev/loop0 /system` + `mount -t erofs` + `pivot_root`. The disk is ESP-only — pure firmware boot target, storage optional.
- Live layout `/boot` = `{vmlinuz, cmdline}` (no initramfs; `uki-cmdline-uk`, no `root=`/`rootwait`).
- Attestation: the ENTIRE OS is inside the measured `.initrd` UKI section → SNP kernel/initrd/cmdline digests + PCR9 UKI event-log replay cover the whole system. The PCR11 system-partition channel is obsolete for enclaves (no partition exists). `S54tpm-rootfs` needs a guard (no `/dev/xvda2` at boot).
- QEMU-verified: `/` = `/dev/loop0` (erofs in RAM), `losetup -a` = `/dev/loop0: 0 /system`, only `vda1` (ESP), tinyssh up.
- kernel only accepts cpio as initrd — raw erofs can't be the `.initrd`; the cpio is the minimal wrapper (one file entry). `initerofs` (LKML 2025-12-31, unmerged) would pin the initrd region for the VM's lifetime and force a writable overlayfs root — rejected for enclaves.
- **AWS-verified (Aug 20): VERDICT: BOUND on live us-east-2 c6a.large** (SEV-SNP + NitroTPM). `verify-binding --uki --no-part`: [2] `.linux`/`.initrd`/`.cmdline` sections byte-match local artifacts (whole OS bound via the measured `.initrd`), [3] PCR4 replay==live, [4] all 12 stub section digests == log + PCR11 replay==live (no partition extend — `--no-part`), [4b] PCR9 predicted, [5] all other PCRs replay==live, [7] SNP v5 report echoes our 64-byte nonce. `S54tpm-rootfs` correctly no-ops (`SKIP no-partition`). `--no-part` replaces the `--disk`/partition-2 path for ESP-only images.
- **Boot regression hit (Aug 20):** first AWS deploy of the unikernel disk never booted (running, no serial, no status checks) — root cause was the FAT16/16KiB ESP; switched to FAT32/4KiB and it booted in ~45 s. QEMU (edk2 202508) booted the FAT16 ESP fine, so **AWS Nitro firmware is the stricter gate — an ESP layout change must be re-tested on AWS, not just QEMU**.

### Completed: SEV-SNP/TPM2 Byte-Level Binding (Aug 15-18, lance/distros)
- **VERDICT: BOUND** — `src/verify-binding` proves SNP + TPM2 attestations describe the same kernel/initrd/cmdline/rootfs on live us-east-2 c6a.large (SEV-SNP + NitroTPM).
- **TPM channel (byte level):** TCG 2.0 crypto-agile event log (dumped from `/dev/mem` at `TPMEventLog=` addr) parsed by `src/elscan.rs`; PCR9 "Linux initrd" + "LOADED_IMAGE::LoadOptions" events are emitted by the kernel's own EFI stub (so their digests == SHA256/384 of our exact initramfs/cmdline); GRUB `tpm` module (added to `packages/box/grub/src/box` module list) measures vmlinuz into the log; full PCR9 replay from zero == live EK-quoted PCR 9.
- **Rootfs channel:** `S54tpm-rootfs` init script extends PCR 11 with SHA256 of raw system partition (erofs, read-only so late measurement is equivalent). Verifier hashes the same partition region of local `disk.img` and checks extend(0, h) == live PCR 11. Partition geometry is deterministic from `box-gpt`: system starts LBA 1050624 (513 MiB), ends at last 1 MiB-aligned boundary; live geometry from `/sys/block/<disk>/<part>/{start,size}` (note: partitions are under the disk dir, NOT flat in /sys/block).
- **Pitfalls hit:** (1) NitroTPM intermittently enters failure states ("commands not being accepted because of a TPM failure") and recovers in seconds — TPM operations at boot need retries; (2) init scripts must be mode 755 (files created by editors default to 644 and rcS `$i start` fails silently — this silently killed S53snptpm-agent and S54tpm-rootfs once); (3) `docker load` of the OCI layout does NOT re-tag `:local` — always `docker tag <new-id> stagex/distro-enclave-dev:{2026.03.0,local}` or the AMI pipeline extracts a stale disk; (4) `chmod` on sources doesn't update mtime, so Makefile sentinels say "nothing to be done" — `rm -rf out/rootfs/distro-enclave-dev out/oci/distro-enclave-dev` to force rebuild; (5) busybox `ls -d A B` prints nothing if B is missing (unlike GNU).
- **Pipeline:** `make distro-enclave-dev` → `make oci-distro-enclave-dev` → `env -C out/oci/distro-enclave-dev tar -cf - . | docker load` → manual `docker tag` → `make aws-ami-deploy` → `make aws-ec2-deploy` → `sh /tmp/verify-new-instance.sh <ip>` (fetches pcrs/cmdline/event log/SNP report/partition geometry, runs verify-binding).
- **Known cosmetic bug (not fixed):** rcS `mark()` NVMe disk-name derivation `${mi_n%?}` yields `nvme0n1p` for `nvme0n1p1`, so rcS boot markers land at the 32 MB fallback seek instead of the ESP tail (initramfs markers are correct).

### Completed: UKI firmware-direct boot + BOUND on QEMU & AWS (Aug 19, lance/distros)
- **Boot model (no GRUB):** firmware boots `\EFI\BOOT\BOOTX64.EFI` directly; the PE entry is `systemd-stub` (assembled by `ukify`), which loads `.linux`, reads `.cmdline`, and handovers to the kernel. GRUB is gone from the enclave trust path.
- **PCR semantics (verified in source + QEMU + AWS):** **PCR4** = OVMF boot-path markers (action strings + boot-option device path), NOT a hash of the UKI — the byte-level UKI binding is carried by section decomposition + PCR11. **PCR5** = OVMF `Tcg2MeasureGptTable` (92-byte GPT header + `u32 count` + `u32 0` + valid non-zero-GUID entries) PLUS an unlogged OVMF boot-order extend → checked by its logged GPT event, excluded from blind replay. **PCR11** = stub measures each UKI section (name+NUL, then data, stub enum order, skipping `.pcrsig`) + `S54tpm-rootfs` `extend(SHA256(system partition))`. **PCR9** = kernel `LOADED_IMAGE::LoadOptions` (`SHA256(UTF-16LE(cmdline)+\x00\x00)`) + `Linux initrd` (`SHA256` of the stub's **combined** initrd = ALIGN4(`.initrd`) + the stub's `.extra/os-release` cpio when `.osrel` present).
- **VERDICT: BOUND on BOTH QEMU and live AWS** (us-east-2 c6a.large, SEV-SNP + NitroTPM, NVMe). `src/verify-binding --uki` reworked: [2] PE-section decomposition (VirtualSize semantics), [3] PCR4 replay==live + PCR5 GPT==local disk, [4] PCR11 predicted section digests + replay+rootfs-extend==live, [4b] PCR9 LoadOptions+initrd predicted, [5] full replay of all other PCRs.

Added `--snp-nonce <file>`: the report's `report_data` must echo back the 64-byte nonce we supplied — an anti-replay freshness proof (QEMU's zeroed dummy report auto-skips).

### Fixed: instances went unreachable at exactly 60 min (Aug 21, lance/distros)
- **Symptom:** deployed c6a.large sat `running`, SSH **timed out** (not refused), status checks `null`, CloudWatch datapoints stopped — every time, at **exactly 3600s (60 min) after boot**. `stop`→`start` (host migration) restored it for another 60 min. A/B on two instances (SNP + non-SNP) both died at exactly +60 min.
- **Root cause:** `dhcpcd` died at boot from a kernel `#GP`, so the 3600s DHCP lease was **never renewed** and expired at +60 min → VPC revoked the ENI's IP → unreachable. dmesg on every boot: `traps: dhcpcd[N] general protection fault ip:… in dhcpcd[…+…]` at the **same binary offset 0x25963** (a plain `mov %r14,%rsi` — an instruction that *cannot* fault), on the `inet_pton(AF_INET6, …)` failure branch ("invalid AF_INET6") in `parse_option`. Reproduced identically on QEMU (KVM) and AWS (Nitro KVM), non-SNP too → guest-side, not SNP.
- **It is a bug in the custom 7.0.0 kernel** (built with `CONFIG_X86_CET=y` + `CONFIG_X86_KERNEL_IBT=y`): a #GP on a valid instruction with correct text bytes (page-cache md5 matched the source exactly) means corrupted CPU state / a CET-IBT interaction in that kernel, not the binary. Not yet pinpointed; worked around in userspace instead.
- **Fix (userspace, verified):**
  - `S03dhcpcd`: run `dhcpcd -4` (IPv4-only) so it never parses DHCPv6/IPv6 addresses → the faulting code path is never reached. dhcpcd stays alive and renews the lease at T1/T2.
  - `S04dhcpcd-watchdog` (new): a detached background loop that restarts dhcpcd (`-4`) if it ever dies — a dead DHCP client must not be a single point of failure. Added as an explicit `COPY` in the enclave Containerfile (init scripts are listed individually, not globbed).
  - Verified: QEMU reboot → no traps, dhcpcd `[ip4]` alive, watchdog running; live AWS SEV-SNP instance → no traps, dhcpcd alive, and `verify-binding` still **VERDICT: BOUND** (rootfs/PCR11 changed as expected, replay from local disk.img matches).
- **Tested mainline 7.2 (Aug 21): did NOT fix it, but we run 7.2 anyway.** Built the 7.2 kernel, booted QEMU with IPv6 enabled (`dhcpcd -b -D`, no `-4`, so the faulting parse path is actually exercised), and got the identical fault at the identical binary offset: `traps: dhcpcd[208] general protection fault ip:…52963 … in dhcpcd[3b963, …]` → offset `0x25963`, same as 7.0. Decision: stay on 7.2 (newer mainline) with the `-4` workaround. Note: to test any future kernel the boot must run dhcpcd WITHOUT `-4`, otherwise "no GPF" is meaningless (the IPv6 parse path is never reached).
- **7.2 live on AWS (Aug 21):** fresh SEV-SNP c6a.large from `ami-0253379985975580b` (instance `i-035b3cdab68e1fa67`) → kernel 7.2.0, no traps, `dhcpcd [ip4]` alive, `verify-binding` **VERDICT: BOUND** (PCR 0/1/2/7/9 all MATCH, SNP nonce echoed). Surviving past 60 min confirmed via monitor. Old 7.0 verification instance `i-0930888cab5c8a4be` terminated.
- **AMI pipeline leak fixed (Aug 21):** `box-aws-ami` gave `tofu apply` output `>/dev/null 2>/dev/null`, so failures were invisible; the real failure was `Maximum policy size of 10240 bytes exceeded for role vmimport` — the tf attached a NEW timestamped inline policy (s3:*/ec2:*) to the `vmimport` role on EVERY run, leaking ~70 policies. Fixed `packages/box/aws-ami/src/aws-ami.tf` to use the fixed policy name `vmimport-s3-policy` (idempotent), deleted the 71 stale policies, and purged 55 leaked `stagex-ami-*` staging S3 buckets (~14GB). The box still does not tear down its staging bucket after import (known leak, each ~260MB).
- **TODO (kernel):** track down the #GP (present in 7.0 AND 7.2; suspect CET/IBT + KVM guest state, or something in the minimal-config kernel build); until then the `-4` workaround is the safe default. If IPv6 is ever needed on the enclave, the watchdog alone is not sufficient (a re-run that hits the same parse path can fault) — fix the kernel first.
- **Build gotcha (7.2):** linux-7.2 added a selftest file with a space in its name (`…/probe/boards/Dell Inc.,XPS 13 9300.yaml`); `src/targets.py` now escapes spaces in Makefile prerequisites (needed for any 7.2+ build).

### Completed: LUKS/TPM2 /home volume (Aug 22-23, lance/distros)
- **Feature:** LUKS2 whole-disk ext4 /home on the data volume, 32-byte key sealed in the NitroTPM, two-stage PCR policy. `S15home` init script (mode 755, `packages/distro/enclave/src/rootfs/etc/init.d/S15home`), runs after udev, before tinyssh.
- **Handles:** 0x81010200 (seed, PCR `5,7`) / 0x81010201 (full, PCR `4,5,7,9`). **NOT 0x81010001** — that is keylime's EK handle (`ek_handle="generate"` in `/etc/keylime/agent.conf`), pre-provisioned on fresh NitroTPMs, so `evictcontrol` there always failed 0x14C ("seal FAILED" on the first attempt at this feature).
- **Two-stage policy:** PCR 4 and 9 DRIFT on the first boot of a fresh AWS instance (firmware initial-boot measurements); PCR 5 and 7 are stable from first boot (verified: first-boot vs steady values differ only in 4/9). PCRs reset+remeasure EVERY boot on both QEMU (tpm-tis power-cycles on guest reboot) and AWS (values identical across reboots) → PCR values are a deterministic function of the boot chain; userspace PCR corruption does NOT survive a reboot (naive fail-closed PCR tests are meaningless — evict the object instead).
- **Flow:** blank disk → drop orphan seed → keygen → **seal seed FIRST (before any disk I/O)** → luksFormat → open → mkfs → mount, every I/O step under a `run_io` deadline (FORMAT 900 s, OPEN 300, MKFS 900, E2FSCK 600, MOUNT 120); on deadline the step is KILLED and boot proceeds with the key kept ("setup incomplete … key kept for next boot"). LUKS disk → unseal full → mount_or_reformat; else unseal seed → migrate seed→full (second boot) → mount_or_reformat; else fail-closed ("locked … /home stays tmpfs", root SSH still works). `mount_or_reformat`: e2fsck → mount; on mount failure mkfs.ext4 recovery + remount (heals an interrupted first boot; verified on AWS Aug 23: volume left as "header + keyslot, no fs" by the old buggy AMI → reboot → ext4 recovered + migrated to full policy).
- **The first-boot "92 % CPU hang" (Aug 23) — root cause found, it was NOT SNP/EBS/kernel:** it was **cryptsetup's argon2 benchmark**. The PBKDF runs inside **OpenSSL 3.6.3's built-in argon2 KDF** — the `fill_block`/`fill_segment`/`kdf_argon2_*` symbols live in `libcrypto.so.3` (the `user-argon2` package is NOT linked; cryptsetup's OpenSSL backend natively supports argon2 when `OSSL_KDF_PARAM_ARGON2_VERSION` exists). The benchmark (2 s target, -5 %/+10 % acceptance band, ONE full measurement per iteration) took **~131 min** to converge on one fresh Nitro boot, finally settling on t=4/m=508008/cpus=2 (sane), then wrote the keyslot and exited. A fresh `luksFormat` on the SAME host completed in 5.4 s — so it was a process/boot-time measurement-noise phenomenon, not the host. Symptom that led the hunt astray: main thread parked in `FUTEX_WAIT_PRIVATE` (pthread_join), worker-thread pairs spawning per argon2 sync point (~0.6 s cadence, `fill_block` in libcrypto), ~1.7 vCPU burned, zero disk I/O after the 32 MB LUKS header write (header JSON has `"keyslots":{}` until the benchmark finishes — keyslot JSON appears only after).
- **Real bug found + fixed:** `run_io` did not kill the step process on deadline expiry → the orphaned luksFormat kept running ~2 h after boot had completed, burning 1.7 vCPU on a 2-vCPU instance (the "instance stuck at 92 % CPU" that survived stop/start). Now `kill -9` on expiry, no `wait` (a D-state process must not block boot; the zombie is reaped by init).
- **PBKDF fix (determinism):** luksFormat now uses `--pbkdf-force-iterations 4 --pbkdf-memory 512000 --pbkdf-parallel $(nproc)` → `CRYPT_PBKDF_NO_BENCHMARK`, no benchmark roulette, ~2 s format, first boot completes in seconds. (Options verified in-guest: `--pbkdf-force-iterations=LONG`, `--pbkdf-memory=kilobytes`, `--pbkdf-parallel=threads` — there is NO `--pbkdf-cpus`; `--pbkdf` takes only the KDF name. `--test-args` dry-runs option parsing.)
- **Verified (Aug 23):** QEMU (fresh swtpm + blank 1 GB vdb): first boot `ok (formatted /dev/vdb, seed pcrs 5,7; full pcrs 4,5,7,9 apply next boot)` in seconds, /home ext4; second boot `ok (luks /dev/vdb, seed pcrs 5,7, migrated to pcrs 4,5,7,9)` + persist file; third boot `ok (luks /dev/vdb, pcrs 4,5,7,9)` + persist file; header kdf = `argon2id time=4 memory=512000 cpus=<nproc>`. AWS non-SNP (prior session): first boot → reboot migration → full policy, all green. AWS self-heal: reboot of the stuck instance (old AMI, volume mid-setup) → mkfs recovery + migration green. Fail-closed QEMU-verified (object evict, since PCR values reset per boot).
- **Final AWS verification (Aug 23, SEV-SNP c6a.large us-east-2, AMI `ami-00f9dff55d148f129`, 10 GB data vol):** first boot hit the documented reachability incident (host-level; stop/start fixed it). The "port 22 still closed 10+ min after migration" was a red herring: **stop/start assigns a NEW public IP** — the old IP was probed the whole time; with the fresh IP the instance was up and S15home had completed (second ESP marker snapshot showed `rcS-done`). Volume was formatted on the first successful boot in seconds (no benchmark hang; header kdf exactly `argon2id time=4 memory=512000 cpus=2`, seed handle 0x81010200 present, full handle absent). ### Completed: Build-time provenance embedding, SPDX 2.3 in the image (Aug 27, lance/distros)
- **Feature:** the enclave image now carries the COMPLETE build-provenance document inside itself. At build time the build computes a full SPDX 2.3 (SPDXTagValue) document — the stagex git origin (credentials stripped), branch, and commit, plus every package in the dependency closure with its name, version, and digests, and the DEPENDS_ON graph — and bakes it into the rootfs at `/provenance.spdx` (packed into disk.img). A booted instance reads its own provenance straight from the image.
- **Why build-time, not launch-time:** the full 217-package document is ~198 KB — far over the 16 KB EC2 user-data cap. The earlier approach squeezed a compact Merkle-root payload into user-data; that is now superseded. Baking the full document into the image removes the user-data size constraint entirely, and provenance is a property of the build (not the launch), which is where it belongs.
- **Opt-in + wiring:** a package sets `provenance = true` in its package.toml (enclave does). `src/targets.py` then inserts a recipe step into that package's `manifest.txt` rule right before the `docker build`: `python3 src/provenance.py <stage>-<name> --embed > packages/<stage>/<origin>/provenance.spdx`, and the Containerfile does `COPY provenance.spdx /provenance.spdx`. The doc is generated AFTER the deps are built (their `out/rootfs/*/manifest.txt` exist) and after the recipe's `rm -rf …/linux_*`, so the doc does NOT include the disk's own hash (no circularity). The generated file is gitignored.
- **`src/provenance.py` modes:** `--embed`/`--raw` = the complete document (one Package per make package + DEPENDS_ON graph: 217 packages, 1651 relationships, ~198 KB); no-flag = the compact Merkle-root document (kept for small-budget consumers). The document is deterministic: `Created` is derived from `SOURCE_DATE_EPOCH` (pinned to 1 in the build) instead of the wall clock, so it is a pure function of (commit, branch, origin, dirty flag, dependency digests).
- **Content:** source package = origin (credentials stripped), `PackageVersion` = commit, `PackageComment: branch=… dirty=N`, `ExternalRef: OTHER git-of-origin …`. Each dependency = `PackageName`, `PackageVersion` (from its package.toml), `PackageChecksum: SHA256:` (rootfs-manifest sha) + `PackageComment: src=…` (chained source-sentinel sha). Relationships = the make dependency graph (DEPENDS_ON).
- **Cutover (launch-time removed):** `aws-ec2-deploy` no longer computes/embeds provenance in user-data (USER_DATA is the SSH key again); `S06cloud-init-net` no longer extracts a provenance block; `S15home` no longer persists `/home/provenance`. The `file("/run/userdata")` HCL interpolation in `box-aws-ec2` stays (robust for multi-line user-data).
- **Verified:** two clean-tree builds → byte-identical disk `04b862475bae00deac7c703a023c85a682ec15a10bdf468df9b8b76728ff7e00`; the guest `/provenance.spdx` is byte-identical to the build-time document and validates as SPDX 2.3 (spdx-tools); guest boots clean (no traps, dhcpcd up). **The disk hash tracks the dirty flag** (the doc records `dirty=N`): a dirty-tree build yields a different hash (e.g. `55a4f3e4…`) than the committed build, so reproducible pins must come from a committed state.
