### Critical: Build Cache Rules
- **NEVER use `NOCACHE=1`** unless intentionally rebuilding the entire tree — it passes `--no-cache` to every `docker build`, destroying all Docker BuildKit cache across all packages.
- **NEVER delete `out/*/` directories** unless you accept a full rebuild — the Makefile depends on OCI layouts at `out/{stage}-{name}/index.json` as build targets. Deleting them breaks dependency resolution.
- **To force a single target rebuild:** only remove that target's output dir, e.g. `rm -rf out/distro-busybox-dev && make distro-busybox-dev`. Leave dependency dirs (`out/core-busybox`, `out/user-linux-server`, etc.) intact.
- **Docker BuildKit is content-addressed:** if source files change, only affected stages rebuild automatically (no NOCACHE needed).

### Distro package layout (Aug 18-19 refactor, lance/distros)
- Distro subpackages split three ways per variant: **default** = live layout (rootfs contents + `/boot` with the three boot objects [vmlinuz, initramfs, cmdline] — no UKI in the live layout); `docker run` gives a shell on the booted filesystem. **`-img`** = scratch + `/disk.img` (box-disk takes the full live layout and does all the packing). **`-vm`** = service-qemu + `/disk.img`.
- `box-uki` (packages/box/uki) is a **pure function**: (vmlinuz, initramfs, cmdline [, os-release]) → the final EFI layout containing ONLY the UKI at `EFI/BOOT/BOOTX64.EFI` (ukify + systemd-stub; deterministic, same inputs → same bytes). If os-release is omitted, ukify 260.2 auto-falls back to the build image's `/etc/os-release` — box-disk always passes the distro's own file explicitly.
- `box-disk` (packages/box/disk) is the single disk assembler, orchestrating the inner boxes: box-uki on `/boot/*` → ESP tree → FAT boot.img sized exactly to the UKI (busybox mcopy: `mcopy -sm $ESP/EFI ::/` puts the tree at the FAT root — copying `$ESP` itself nests it under `::/esp`), box-erofs → system.img (live layout minus `/boot`), box-gpt → GPT `disk.img`.
- **ESP/disk sizing (Aug 20):** the ESP is sized to the UKI, not a fixed 512 MiB. **Always FAT32 with 4 KiB clusters** (padded to FAT32's 65525-cluster minimum, ~256 MiB). UKI volume serial pinned (`-i 0x53544147`). `box-gpt` derives the ESP partition size from the boot.img file; ESP-only (unikernel) disk = ESP + 2 MiB tail for the alternate GPT header. **Why not FAT16:** an earlier revision used FAT16 with 16 KiB clusters for UKIs under 1 GiB, and it booted in QEMU (edk2 202508) but **never booted on AWS Nitro UEFI** (instance sat `running`, no serial output, no status checks, port 22 closed) — the old Nitro firmware does not boot that ESP. The pre-UKI AWS-working image used FAT32, and FAT32/4KiB ESPs boot on AWS (verified Aug 20: port 22 open ~45 s after launch). Enclave disk.img: 528 → **259 MiB** (257 MiB ESP).
- The booted system **never mounts the ESP** (no `/boot`, no vfat mount in the guest): rcS/initramfs write progress markers by raw `dd` seeks to the ESP tail. So the final ESP legitimately contains only the UKI (kernel/initrd/cmdline live inside it, verified byte-identical in [2]).
- `box-grub` with `TREE_ONLY=1` leaves the ESP tree at /boot + /efi instead of packing a FAT image (embed distro still uses the default packing path; embed is a separate GRUB/limine flow).
- Consumers of disk.img use the `-img` subpackage: `make distro-enclave-dev-img`, `out/rootfs/distro-enclave-dev-img/linux_amd64/disk.img`; aws-ami extracts via plain `cp` from the local export (the -img image has no command, so `docker create` on it fails).
- erofs images are NOT bit-deterministic across builds (internal NIDs/layout differ), so any measurement pin over the erofs bytes changes per build; the binding stays valid because local artifacts and the live system come from the same build. The UKI itself IS bit-deterministic for fixed inputs (same kernel/initrd/cmdline/osrel/stub → same bytes, e.g. `c913d89c…` across rebuilds in disk mode). Note: in unikernel mode the initrd embeds the erofs, so the UKI changes per build too.
- **Re-verified after restructure:** disk with UKI-only ESP boots QEMU and `verify-binding --uki` → **VERDICT: BOUND** (PCR4/5/9/11 pins unchanged from the pre-restructure BOUND run).

### Unikernel enclaves (Aug 19, lance/distros)
- Enclaves run fully from RAM: `box-disk` with `UNIKERNEL=1` packs the OS as erofs, wraps it as `/system` inside a tiny cpio `{nit (as /init), /system}`, and uses that cpio as the UKI's `.initrd`. nit is the static Rust unikernel init (fetched from codeberg.org/lrvick/nit via `packages/user/nit`), which does what the old dash + 5-klibc-utils `init-loop` did: `losetup /dev/loop0 /system` + `mount -t erofs` + `pivot_root`. In `nit.mode=spawn` nit then stays PID 1: it runs the inittab `::sysinit:/etc/init.d/rcS` (all S??* scripts), respawns `/bin/getty 115200 ttyS0`, and runs `::shutdown:` on halt. The disk is ESP-only — pure firmware boot target, storage optional. The initramfs cpio carries no shell, no klibc utils, no busybox.
- Live layout `/boot` = `{vmlinuz, cmdline}` (no initramfs; `uki-cmdline-uk` carries `nit.unpack=/system nit.mode=spawn`, no `root=`/`rootwait`).
- Attestation: the ENTIRE OS is inside the measured `.initrd` UKI section → SNP kernel/initrd/cmdline digests + PCR9 UKI event-log replay cover the whole system. The PCR11 system-partition channel is obsolete for enclaves (no partition exists). `S54tpm-rootfs` needs a guard (no `/dev/xvda2` at boot).
- QEMU-verified (Sep 4, nit): `/` = `/dev/loop0` (erofs in RAM), `losetup -a` = `/dev/loop0: /oldroot/system`, only `vda1` (ESP), dhcpcd ip4 up, tinyssh :22 up (tcpserve-owned), getty on ttyS0, LUKS /home ext4 on the data disk, zero traps/#GP/CFI/UBSAN in dmesg, all 12 S??* ran, nit = PID 1.
- kernel only accepts cpio as initrd — raw erofs can't be the `.initrd`; the cpio is the minimal wrapper (two entries: `/init` = nit, `/system` = the erofs). `initerofs` (LKML 2025-12-31, unmerged) would pin the initrd region for the VM's lifetime and force a writable overlayfs root — rejected for enclaves.
- **AWS-verified (Aug 20): VERDICT: BOUND on live us-east-2 c6a.large** (SEV-SNP + NitroTPM). `verify-binding --uki --no-part`: [2] `.linux`/`.initrd`/`.cmdline` sections byte-match local artifacts (whole OS bound via the measured `.initrd`), [3] PCR4 replay==live, [4] all 12 stub section digests == log + PCR11 replay==live (no partition extend — `--no-part`), [4b] PCR9 predicted, [5] all other PCRs replay==live, [7] SNP v5 report echoes our 64-byte nonce. `S54tpm-rootfs` correctly no-ops (`SKIP no-partition`). `--no-part` replaces the `--disk`/partition-2 path for ESP-only images.
- **Boot regression hit (Aug 20):** first AWS deploy of the unikernel disk never booted (running, no serial, no status checks) — root cause was the FAT16/16KiB ESP; switched to FAT32/4KiB and it booted in ~45 s. QEMU (edk2 202508) booted the FAT16 ESP fine, so **AWS Nitro firmware is the stricter gate — an ESP layout change must be re-tested on AWS, not just QEMU**.

### Completed: UKI firmware-direct boot + BOUND on QEMU & AWS (Aug 19, lance/distros)
- **Boot model (no GRUB):** firmware boots `\EFI\BOOT\BOOTX64.EFI` directly; the PE entry is `systemd-stub` (assembled by `ukify`), which loads `.linux`, reads `.cmdline`, and handovers to the kernel. GRUB is gone from the enclave trust path.

### Fixed: instances went unreachable at exactly 60 min (Aug 21, lance/distros)
- **Symptom:** deployed c6a.large sat `running`, SSH **timed out** (not refused), status checks `null`, CloudWatch datapoints stopped — every time, at **exactly 3600s (60 min) after boot**. `stop`→`start` (host migration) restored it for another 60 min. A/B on two instances (SNP + non-SNP) both died at exactly +60 min.
- **Root cause:** `dhcpcd` died at boot from a kernel `#GP`, so the 3600s DHCP lease was **never renewed** and expired at +60 min → VPC revoked the ENI's IP → unreachable. dmesg on every boot: `traps: dhcpcd[N] general protection fault ip:… in dhcpcd[…+…]` at the **same binary offset 0x25963** (a plain `mov %r14,%rsi` — an instruction that *cannot* fault), on the `inet_pton(AF_INET6, …)` failure branch ("invalid AF_INET6") in `parse_option`. Reproduced identically on QEMU (KVM) and AWS (Nitro KVM), non-SNP too → guest-side, not SNP.
- **It is a bug in the custom 7.0.0 kernel** (built with `CONFIG_X86_CET=y` + `CONFIG_X86_KERNEL_IBT=y`): a #GP on a valid instruction with correct text bytes (page-cache md5 matched the source exactly) means corrupted CPU state / a CET-IBT interaction in that kernel, not the binary. Not yet pinpointed; worked around in userspace instead.
- **Fix (userspace, verified):**
  - `S03dhcpcd`: run `dhcpcd -4` (IPv4-only) so it never parses DHCPv6/IPv6 addresses → the faulting code path is never reached. dhcpcd stays alive and renews the lease at T1/T2.
  - `S04dhcpcd-watchdog` (new): a detached background loop that restarts dhcpcd (`-4`) if it ever dies — a dead DHCP client must not be a single point of failure. Added as an explicit `COPY` in the enclave Containerfile (init scripts are listed individually, not globbed).
  - Verified: QEMU reboot → no traps, dhcpcd `[ip4]` alive, watchdog running; live AWS SEV-SNP instance → no traps, dhcpcd alive, and `verify-binding` still **VERDICT: BOUND** (rootfs/PCR11 changed as expected, replay from local disk.img matches).
- **Tested mainline 7.2 (Aug 21): did NOT fix it, but we run 7.2 anyway.** Built the 7.2 kernel, booted QEMU with IPv6 enabled (`dhcpcd -b -D`, no `-4`, so the faulting parse path is actually exercised), and got the identical fault at the identical binary offset: `traps: dhcpcd[208] general protection fault ip:…52963 … in dhcpcd[3b963, …]` → offset `0x25963`, same as 7.0. ### Completed: LUKS/TPM2 /home volume (Aug 22-23, lance/distros)
- **Feature:** LUKS2 whole-disk ext4 /home on the data volume, 32-byte key sealed in the NitroTPM, two-stage PCR policy. `S15home` init script (mode 755, `packages/distro/enclave/src/rootfs/etc/init.d/S15home`), runs after udev, before tinyssh.
- **Handles:** 0x81010200 (seed, PCR `5,7`) / 0x81010201 (full, PCR `4,5,7,9`). **NOT 0x81010001** — that is keylime's EK handle (`ek_handle="generate"` in `/etc/keylime/agent.conf`), pre-provisioned on fresh NitroTPMs, so `evictcontrol` there always failed 0x14C ("seal FAILED" on the first attempt at this feature).
- **Two-stage policy:** PCR 4 and 9 DRIFT on the first boot of a fresh AWS instance (firmware initial-boot measurements); PCR 5 and 7 are stable from first boot (verified: first-boot vs steady values differ only in 4/9). PCRs reset+remeasure EVERY boot on both QEMU (tpm-tis power-cycles on guest reboot) and AWS (values identical across reboots) → PCR values are a deterministic function of the boot chain; userspace PCR corruption does NOT survive a reboot (naive fail-closed PCR tests are meaningless — evict the object instead).
- **Flow:** blank disk → drop orphan seed → keygen → **seal seed FIRST (before any disk I/O)** → luksFormat → open → mkfs → mount, every I/O step under a `run_io` deadline (FORMAT 900 s, OPEN 300, MKFS 900, E2FSCK 600, MOUNT 120); on deadline the step is KILLED and boot proceeds with the key kept ("setup incomplete … key kept for next boot"). LUKS disk → unseal full → mount_or_reformat; else unseal seed → migrate seed→full (second boot) → mount_or_reformat; else fail-closed ("locked … /home stays tmpfs", root SSH still works). `mount_or_reformat`: e2fsck → mount; on mount failure mkfs.ext4 recovery + remount (heals an interrupted first boot; verified on AWS Aug 23: volume left as "header + keyslot, no fs" by the old buggy AMI → reboot → ext4 recovered + migrated to full policy).
- **The first-boot "92 % CPU hang" (Aug 23) — root cause found, it was NOT SNP/EBS/kernel:** it was **cryptsetup's argon2 benchmark**. The PBKDF runs inside **OpenSSL 3.6.3's built-in argon2 KDF** — the `fill_block`/`fill_segment`/`kdf_argon2_*` symbols live in `libcrypto.so.3` (the `user-argon2` package is NOT linked; cryptsetup's OpenSSL backend natively supports argon2 when `OSSL_KDF_PARAM_ARGON2_VERSION` exists). The benchmark (2 s target, -5 %/+10 % acceptance band, ONE full measurement per iteration) took **~131 min** to converge on one fresh Nitro boot, finally settling on t=4/m=508008/cpus=2 (sane), then wrote the keyslot and exited. A fresh `luksFormat` on the SAME host completed in 5.4 s — so it was a process/boot-time measurement-noise phenomenon, not the host. Symptom that led the hunt astray: main thread parked in `FUTEX_WAIT_PRIVATE` (pthread_join), worker-thread pairs spawning per argon2 sync point (~0.6 s cadence, `fill_block` in libcrypto), ~1.7 vCPU burned, zero disk I/O after the 32 MB LUKS header write (header JSON has `"keyslots":{}` until the benchmark finishes — keyslot JSON appears only after).
- **Real bug found + fixed:** `run_io` did not kill the step process on deadline expiry → the orphaned luksFormat kept running ~2 h after boot had completed, burning 1.7 vCPU on a 2-vCPU instance (the "instance stuck at 92 % CPU" that survived stop/start). Now `kill -9` on expiry, no `wait` (a D-state process must not block boot; the zombie is reaped by init).

### Completed: BuildKit local-context cache fix — content-hash mtimes (Sep 7, lance/distros)
- **Bug:** `make` silently packed a **STALE** bootproof into the disk after the dependency was rebuilt. BuildKit's local-context cache is **per-file, keyed on (path, size, mtime)**. The `type=local` exporter clamps every context mtime to `SOURCE_DATE_EPOCH` (exported by **`src/global.mk:5 export SOURCE_DATE_EPOCH=1`** — BuildKit reads it from the build *client environment*, not just `--build-arg`; the local template's `--build-arg SOURCE_DATE_EPOCH=1` is redundant with this), so old/new artifacts that are byte-identical in SIZE (bootproof swap: both 8844776 B) got the same key → cache "unchanged" → BuildKit served the cached (stale) context (smoking gun: `transferring stagex/user-bootproof: 617B` instead of ~12.85 MB).
- **Marker file does NOT fix it (tested):** the cache is per-file, not a directory fingerprint — a sibling `.buildstamp` with a fresh mtime busts only its own entry; the stale `bootproof` entry is still `(path, size, epoch-1)` and is still served. Do not use a marker.
- **Fix (in `src/fixrootfs.sh`, runs after the local export):** re-stamp every file's mtime to a **deterministic function of its content**: `mtime = int(sha256(file)[:8], 16)` (32-bit epoch seconds, range 1970–2106, e.g. 2093 for bootproof). Changed content → different mtime → per-file cache MISS → fresh context served; unchanged content → same mtime → cache HIT (fast, and the hash IS the content so the served bytes are correct by construction). Symlinks are keyed by their target string. Single-pass python3 (hashlib + `os.utime(..., follow_symlinks=False)`).
- **Why the weird "future" dates are correct, not a bug:** a *constant* mtime is the original bug (same-size swap invisible); the value must move with the bytes. Full 32-bit width is the maximally injective key (any remap into a narrower window increases collisions). The dates are cosmetic: they never reach the disk (box-erofs `--ignore-mtime --force-uid/gid=0`; box-disk touches cpio + ESP tree to `SOURCE_DATE_EPOCH`; provenance.spdx `Created` derives from `SOURCE_DATE_EPOCH`).
- **Proof (Sep 7):** BuildKit A/B (H0/H1/H2, same 8844776 B, vary only mtime): seed=OLD → swap NEW(hash mtime) → cache MISS serves NEW → swap back OLD(hash mtime) → cache HIT serves OLD. End-to-end: single `make distro-enclave-dev-img` (no NOCACHE) → build log `transferring stagex/user-bootproof: 12.85MB` (fresh, not 617 B) → disk erofs `bootproof` = context sha (marker 0 = NEW). Determinism: two rebuilds → **byte-identical disk.img** (`7f79609e…` both). QEMU boot of the packed bytes: guest `/usr/bin/bootproof` = NEW sha, zero traps/GPF/UBSAN.
- **Discipline:** ground truth is always `out/` (context dirs + disk.img), never Docker tags (`docker load` does not re-tag `:local`; `stagex/distro-enclave-dev:local` showed the OLD marker 1 while the disk carried NEW — the tag is stale, ignore it). To verify what's *in the disk*, extract: `sfdisk -d` (ESP = LBA 2048, 526336 sectors) → `dd bs=512 skip=2048` → `mcopy -i boot.img ::/EFI/BOOT/BOOTX64.EFI UKI.efi` (mcopy takes a destination ARG, not a shell redirect) → parse PE sections (`.initrd` = raw file offset, gzip) → cpio is **newc** (96 bytes of 8-hex-digit fields, NOT binary u32) → `/system` = erofs → mount (`docker run --privileged -v scratch:/work stagex/service-qemu:local -c 'mount -o ro,loop /work/system.erofs /mnt'` — host loop setup is not permitted).

- **Verified configs (built kernel):** CONFIG_SCSI=y, CONFIG_BLK_DEV=y, CONFIG_BLK_DEV_SR=y, CONFIG_CDROM=y, CONFIG_ISO9660_FS=y, CONFIG_SCSI_VIRTIO=y, CONFIG_SCSI_LOWLEVEL=y — all correct
- Tried: IDE CD-ROM, AHCI SATA CD-ROM, virtio-scsi CD-ROM, -cdrom flag, PIIX3 IDE — same result. Not a QEMU args issue.
- Likely kernel bug/incompatibility in minimal config where SR driver sees device but never creates block device sysfs entry
